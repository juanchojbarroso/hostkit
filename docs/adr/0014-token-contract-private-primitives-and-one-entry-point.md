# 0014. Token contract: private primitives, system-colour fallback, one entry point

## Context and problem statement

ADR-0012 Q5 says renaming any token (`--hk-*`) is breaking, but it doesn't
say *which* tokens are public. ADR-0003 keeps three layers (primitive →
semantic → component) in separate files. Three questions follow: may a
consumer use primitives like `blue-600`? What does a component look like
when the host forgets to load the tokens CSS? And which file does a
consumer import?

## Decision drivers

- Freedom to rework the palette without a major release
- A forgotten setup step must not produce an inaccessible component
- No hard-coded colours in components (definition of done)
- The layer split exists for our Style Dictionary migration (ADR-0003),
  not for consumers
- No build step for tokens yet (ADR-0003)

## Considered options

**Primitive visibility**

1. Primitives private (`--_hk-*`); semantic and component tokens public
2. Primitives public (`--hk-blue-600`), covered by Q5
3. No primitive layer; semantic tokens hold raw values

**Fallback without tokens CSS**

1. None: tokens are required
2. Hard-coded brand fallbacks (`var(--hk-color-action-primary, #1d4ed8)`)
3. CSS system colours as the last fallback (`ButtonFace`, `ButtonText`, `Highlight`)
4. Components inject the tokens themselves

**Entry point**

1. One public `tokens.css` that `@import`s private layer files
2. One public file generated by a concatenation script
3. Every layer file exported

## Decision outcome

Chosen:

- **Primitives are private.** They're named `--_hk-*`; the leading
  underscore marks "not API". Only semantic tokens (`--hk-color-*`, …)
  and component tokens (`--hk-<component>-*`) are public, and only
  those are covered by ADR-0012 Q5. Option 3 would contradict ADR-0003.
- **System colours are the fallback.** Each component custom property
  falls back through its semantic token to a CSS system colour. Without
  tokens, a component looks like a native browser control: plain, but
  usable, accessible, and correct in forced-colours mode. Brand colours
  live in exactly one place, `@hostkit-ui/tokens`. Option 4 is rejected:
  a global side effect from a component import, and a collision source
  when two versions share a page (M3).
- **`@hostkit-ui/tokens/tokens.css` is the only public entry.** It
  `@import`s the layer files, which are not in `exports`.

Phase 0 semantic tokens: `--hk-color-action-primary`,
`--hk-color-action-primary-text`, `--hk-color-action-secondary`,
`--hk-color-action-secondary-text`, `--hk-color-focus-ring`.

### Consequences

- Good: the palette can change freely; only meaning is contract
- Good: a missing stylesheet degrades to a native-looking control, not a
  broken one
- Good: the internal file structure can change without a major
- Bad: consumers who want a raw palette colour can't have one; they must
  ask for a semantic token
- Bad: on the CDN, `@import` causes a small waterfall of sequential
  requests
- Bad: the system-colour fallback looks unbranded, which may hide a
  missing stylesheet during development
- Validation: a component test runs axe with no tokens stylesheet
  loaded; publint confirms the layer files aren't reachable via `exports`
- Revisit when: tokens move to Style Dictionary (ADR-0003), which can
  generate one file and remove the `@import` waterfall; or a consumer
  shows a real need for primitives

## Lesson

Expose meaning, not raw material. Every name you publish becomes a
promise, so publish only the names whose meaning you're willing to keep.
